# DASH ProfitDLL gateway

This gateway is the selected adapter for DASH. It is a separate Windows x64 process and must not change or share account state with `gateways/mt5/`, which remains the DAWN path.

## Current status

- Provider ID in `config/daytrade.json`: `PROFITDLL_DAYTRADE`.
- Before prompting for Nelogica credentials, the gateway authenticates with the quote and history preflight endpoints and checks the configured instrument plus both Supabase stores. A failed preflight stops startup before any broker login.
- The application-side read-only quote intake is implemented at `POST /api/daytrade/quote`; a dedicated `PROFITDLL_INGEST_SECRET` protects it separately from scheduler credentials. The endpoint validates the configured contract and freshness against the API server's receive time (the gateway timestamp is checked for clock skew only), then calls one database transaction that rejects stale quote sequences and stores the quote and its 1-minute OHLCV bars atomically. Bars carry their source exchange timestamp so a delayed concurrent request cannot overwrite a newer snapshot. Owner-scoped RLS allows reads; only the service role writes. DASH migrations are applied and synchronized through `20261103025606_daytrade_paper_session_boundary_gap`; confirm remote history before future migrations. The market and paper tables are still empty until the ProfitDLL gateway is authorized and connected.
- `gateway.py` is a read-only Windows x64 consumer. It uses the documented Market Data initialization, keeps callbacks short, translates trades while native pointers are valid, waits for login/feed/activation states, aggregates ticks into 1-minute OHLCV bars plus trade turnover (`price × quantity`) and relays rate-limited quote snapshots and bars over HTTPS. It never loads OMS order functions.
- For historical trades, the gateway prefers Nelogica's currently documented `SetHistoryTradeCallbackV2` export and falls back to the legacy `SetHistoryTradeCallback` name when that is the only export available. Both use the documented by-value asset and expanded trade fields; startup fails clearly if neither symbol exists. It also rejects a duplicate trade number within the requested session, since that field is documented as unique for the session. This accommodates the different function names in [Nelogica's current function map](https://ajuda.nelogica.com.br/hc/pt-br/articles/11168755650459-Fun%C3%A7%C3%B5es-Real-Time-DLL) and [dedicated history example](https://ajuda.nelogica.com.br/hc/pt-br/articles/11973319153563-Como-requisitar-trades-hist%C3%B3ricos-com-a-ProfitDLL).
- Both callbacks must identify `FeedType/feed = 0` (Nelogica). The documented alternate-source value `255` and any other value invalidate the live minute or historical session instead of being persisted as ProfitDLL-originated data.
- On startup, the authenticated history preflight returns the sessions actually persisted in Supabase for the prior 30 calendar days. A separate bounded worker requests only missing days from ProfitDLL, aggregates the regular session into M1 candles, and posts completed sessions to `POST /api/daytrade/history`. Daily callback progress must reach 100 before data is sent. Supabase is authoritative; no local state file can make the gateway skip a session missing from the database. Empty days are retried on a later startup and never recorded as imported sessions. Reimports replace the complete validated day, update its session marker, and remove stale minutes or colliding live candles. Historical bars have `PROFITDLL_HISTORY` provenance. Historical callback errors discard that day's import; live collection continues independently.
- A ProfitDLL transition out of READY discards the in-memory current and unsent candles and pauses aggregation through the current minute. The collector resumes only in a new minute, so ticks lost during a brief feed interruption cannot be blended into an apparently complete OHLCV candle.
- Historical M1 imports preserve minutes with no trades as absent bars; the API does not fabricate zero-volume OHLC. Chart time spacing keeps the gaps visible. Walk-forward may use sparse days only when the persisted completed-session marker matches the imported bar count; after the first gap it closes an open paper position at the next available candle and stops that day's simulation. The opening range still needs all 15 observed minutes.
- DASH order submission remains blocked in the application. The official licensed DLL runtime must be installed locally before connecting.

## Integration order

1. Install the official Nelogica x64 package and activation on a dedicated Windows environment. Keep the DLL, support files, activation code, Nelogica login, and broker account credentials out of Git, browser code, application logs, and deployment bundles.
2. Start with read-only market data only after the exact contract symbol and entitlement are confirmed. The PowerShell launcher prints the DLL file version; compare it with the version and headers in the licensed SDK. The gateway reads the PE version resource before making HTTP requests or loading the vendor DLL, and currently permits only `4.0.0.41`, the version named by Nelogica's public binding example. The locally installed DLL was file version `4.0.0.42` on 2026-11-02; its signature is valid but the ABI remains unverified because its folder has no header or release notes. It is therefore rejected before any login prompt. Do not add a version to the allowlist until the licensed SDK/header or official release notes confirm the callback ABI. Historical data is requested by day, within Nelogica's published 30-day retention, and only completed prior sessions are imported.
3. Run `gateway.py` with Python Windows x64. Set `PROFITDLL_RUNTIME_DIR` to the official package `DLLs/Win64` directory, `PROFITDLL_TICKER` to the same verified current contract symbol as `config/daytrade.json`, `PROFITDLL_EXCHANGE=F`, `DASH_API_URL=https://<deployment>/api/daytrade/quote`, and the dedicated `PROFITDLL_INGEST_SECRET`. The process prompts for activation key, Nelogica username, and password; it does not put them in files or command-line arguments. After changing `PROFITDLL_INGEST_SECRET` in Vercel, create a new deployment so the runtime receives that value, then run the gateway script's quote and history preflights. Both must report `READY` before the gateway asks for Nelogica credentials.
4. Use a separate authenticated command channel for application health and controls. The gateway must not expose an unauthenticated listener on the public internet; prefer outbound authenticated polling or a separately reviewed private network. Vercel does not host the native DLL process.
5. Add OMS routing only after the broker confirms that this account is enabled for routing, the licensed DLL mode supports the required account/instrument/order types, and order/position queries support reliable reconciliation. Treat the DLL's synchronous `SendOrder` ID as dispatch acknowledgement only; confirm broker acceptance and later state through callbacks and queries.
6. Keep live sending disabled until instrument specs, risk limits, idempotency, durable journal, stop/exit handling, reconnect recovery, independent halt, shadow operation, and operational approval are implemented and reviewed.

## Local gateway configuration

Keep the vendor package outside the repository. Never place the activation key, credentials, or ingest secret in Git or browser code. Store the ingest secret in the private gateway environment and the Vercel server environment; use a distinct value from CRON_SECRET. The current read-only contract is WINZ26 (expires 16/12/2026), with B3 public tick/value specs recorded in `config/daytrade.json`. The endpoint rejects new quotes after expiry. Before rolling the contract, confirm the new expiry and update the symbol in the config and local `.env.local`; never reuse an expired symbol. Market Data entitlement and Nelogica activation remain required.

## Quick start after obtaining the official package

1. Download the **ProfitDLL Windows x64** package from Nelogica's official logged-in area. Do not use DLLs from third-party mirrors. Extract it to a private local folder and point `PROFITDLL_RUNTIME_DIR` at the folder containing `ProfitDLL.dll`.
2. Install Python 3 for Windows x64 if it is not already installed.
3. Open PowerShell at the repository and run `./gateways/profitdll/run-gateway.ps1`. On first run, the script creates the ignored local `gateways/profitdll/.env.local` from `.env.example`; fill in the runtime, deployed quote URL, and dedicated ingest secret, then run it again. The script checks the configured contract and local runtime, then asks for the activation key and Nelogica credentials in hidden prompts. Use a randomly generated secret of at least 32 characters, distinct from `CRON_SECRET`; the script rejects a placeholder, a short value, or reuse of the scheduler secret.
4. Keep the collector running during the market session. The dashboard's **Gráficos** tab polls the 1-minute candles and strategy observation from `/api/daytrade/bars`.

The first run backfills up to 30 calendar days of completed historical trades available to the license, then continues live Market Data collection. The Nelogica package/license may limit available days; missing, incomplete, special-session, or unverified-calendar sessions are not treated as complete backtest samples. This pipeline is read-only: the integration uses Market Data initialization and does not load ProfitDLL OMS/order functions. Real orders remain disabled.

The DASH also has a separate forward paper simulator. The owner enters account-specific margin, per-side costs, session limits and risk limits in the authenticated **Risco** tab; the values are stored per owner in `dt_settings` and journaled. The simulator stays idle until the source is confirmed and every readiness gate passes. It simulates next-minute fills in its own `dt_paper_*` tables; it never sends orders through ProfitDLL or changes ATLAS/DAWN positions.

The configured WINZ26 symbol should be rolled before its 16/12/2026 expiry. The B3 WIN schedule is 09:00–18:25 from 03/11/2026; the contract's expiry day closes at 18:00. Check the [B3 circular 055/2026](https://www.b3.com.br/data/files/BE/16/C1/59/2F881A10F75B881AAC094EA8/OC%20055-2026-VNC%20NOVOS%20HORARIOS%20DE%20NEGOCIACAO_PT.pdf).

The collector buffers closed candles across the one-second snapshot throttle and across transient endpoint failures, then retries them only alongside a fresh quote. It rejects out-of-order/duplicate trade events and reports queue drops. Candles older than the API's two-minute intake window are discarded with a warning; downstream paper/backtest continuity checks must continue to treat those intervals as gaps.

Each candle stores the sum of execution price multiplied by trade quantity. The DASH uses `turnover / volume` for trade-weighted VWAP. Legacy candles without turnover remain readable, but VWAP strategy analysis waits for complete trade totals rather than substituting closing-price-weighted approximations.

On any dropped, malformed (non-finite/non-positive price or non-positive quantity), untranslatable, flagged, duplicate, or out-of-order trade, callback/ABI decoding exception, or stale in-memory candle after a long disconnect, the gateway clears unsent bars and waits for the next minute bucket. Nelogica's current guide identifies bit 0 of the `c_uint` flags argument as an edit event. Since the gateway does not yet revise an aggregated trade by trade number, edited trades and unknown flag bits are quarantined instead of being applied as corrections. This intentionally creates a visible data gap instead of persisting potentially wrong OHLCV. A transient HTTP failure alone does not clear the buffer; the next current quote may carry recent closed candles if they remain inside the API intake window.

Live and historical trades also require a documented `TradeType` (1–13). Nelogica classifies type `32` as unknown; it and any future undocumented value invalidate the current live sample or historical session. The documented buy/sell aggression values (2/3) remain part of OHLCV turnover, but the strategy does not yet treat them as a directional signal. Reference: [Nelogica historical trades and TradeType](https://ajuda.nelogica.com.br/hc/pt-br/articles/11973319153563-Como-requisitar-trades-hist%C3%B3ricos-com-a-ProfitDLL).
